Last updated: 2026-09-16. Owner: Wyrlo.

Naming: "FoqusLab" is the product name. "OptoPrep" is the old name, still used informally with
the alpha users. They mean the same app. See `ventures/foquslab/app/rebrand-log.md`.

## 1. What it is

A gamified optometry board-review web app for the Philippine Optometry Licensure Exam (OLE).
It carries the full 8-subject board content as reviewers, subject exams, preboards, mock
boards, and a CBT simulator, plus a spaced-repetition review queue, a readiness tracker, and
light game mechanics (streaks, tickets, floors).

Today it runs as an approved-alpha tool: a handful of batchmates plus the admin. Signups are
manual-approved. The paid product and public launch are post-boards work (see section 16).

```
supabase-setup.sql     base tables (exam_attempts, app_settings, app_events)
exam-build/            Python pipeline that builds the Top 2 static HTML from JSON banks
  banks/<A-H>.json     source of truth for Top 2 subject-exam content
  additions/, patches/ author-new and fix-existing question inputs
  *.py                 lint_bank, build_exams, add_questions, apply_patch, build_mock, ...
  backfill_srs_payload.mjs / .sql   repair review-queue cards after a question fix

                       CBLE simulator, cards, master index. Built artifacts, do not hand-edit
                       the subject exams (regenerate from banks).
docs/                  this file + ARCHITECTURE-CONSOLIDATION-PLAN + ACCESS-CONTROL-SPEC
```

Two front-end stacks live side by side (this is the central maintenance fact):

- The **React / Next.js app** powers practice, exam, drill, review, notes, readiness, admin,
  account, search. Behavior lives once in shared components and routes.
- The **Top 2 area** is 162 static HTML pages under `public/top2/`, generated by Python in
  `exam-build/`. Each page ships its own embedded copy of its questions and its own quiz JS.

Consequence: a single question can exist in more than one place (a bank, a preboard page, a
main-app JSON), and a fix in one copy does not reach the others. See section 15.

## 6. Data model (Supabase)

All tables use row-level security. Users reach only their own rows. Cross-user writes happen
server-side through admin API routes using the service-role key, which bypasses RLS.

| Table | Purpose | Key columns |
|---|---|---|
| `profiles` | one row per user, the account record | `user_id`, `full_name`, `email`, `approved`, `approval_token`, `tier`, `grants[]`, `suspended`, `blocked_until`, `force_logout_at`, `last_active`, `role` |
| `question_reviews` | the SRS review queue, one row per (user, question) | `question_id` (FNV-1a of normalized stem), `subject`, `source`, `payload` (jsonb snapshot), `box`, `due_on`, `reps`, `lapses`, `retired` |
| `ole_attempts` | scored Top 2 attempts, feeds readiness | `subject_code` (A-H), `source`, `score`, `total`, `percentage`, `area_breakdown`, `wrong_topics` |
| `exam_attempts` | scored main-app exams | `subject`, `score`, `total`, `percentage`, `wrong_questions` |
| `daily_queue` | Daily Queue check-offs, synced across devices | `item_id` ("<dayIndex>_<ticketIndex>"), `checked` |
| `app_settings` | single-row app config | `maintenance_mode` |
| `app_events` | page-view analytics for the admin Usage tab | `type`, `path`, `ip`, `ua`, `created_at` |
| reading progress | Top 2 reading position tracking | (see `supabase/reading-progress.sql`) |

Schema is stored as `.sql` files in `supabase/` and applied by hand in the Supabase SQL
editor. There is no automated migration runner. `supabase-setup.sql` holds the base tables;
the feature tables live in their own files.

The question payload is stored **on** the review row rather than referenced by id. The Top 2
questions are embedded in static HTML the server cannot read at request time, so a snapshot is
the only way one queue can serve both the app banks and the Top 2 pages.

## 7. Access control and tiers

Rules live in one place: `src/lib/access.ts` and `src/lib/reviewer-manifest.ts`. The client
never decides access. The full spec is `docs/ACCESS-CONTROL-SPEC.md`.

Two separate ideas:

- **Tier** (shape of access): `base`, `select`, `full`, `admin`.
- **Grants** (exact content): a per-user array of item IDs, for example `["A.exam",
  "A.preboards-set2"]`.

| Tier | Original app | Top 2 items | Cockpit index |
|---|---|---|---|
| `base` | yes | none except items marked public | no |
| `select` | yes | only granted items | no (reaches items via home cards) |
| `full` | yes | only granted items | yes (filtered to granted items) |
| `admin` | yes | everything | yes |

Admin is also anyone matching `ADMIN_USER_ID` or `ADMIN_EMAIL` in env. That is the master
override regardless of the `tier` column.

Content manifest: `src/lib/reviewer-manifest.ts` has one entry per grantable item. It drives
the middleware gate, the cockpit, the home cards, and the admin toggles. To add or restructure
grantable content, edit the manifest; nothing else hard-codes Top 2 paths.

Review cards are re-authorized on every serve: a card stores a question snapshot, so without a
check, revoking a grant would leave stems readable through `/review`. `canServeCard` in
`access.ts` re-checks each card against current access.

## 8. Auth and account lifecycle

- Sign up on `/signup`. A Postgres trigger auto-creates the `profiles` row (`handle_new_user`,
  SECURITY DEFINER).
- New users start `approved = false`, `tier = 'base'`, empty grants. They land on `/pending`.
- Admin approves them (admin UI or the approval email link). Approval is manual today.
- `middleware.ts` runs on nearly every request and enforces, in order: auth presence,
  maintenance mode, approval gate, force-logout stamp, suspension, per-user timed block, and
  Top 2 item gating. Every DB check has a 4s timeout and fails open (except auth), so a slow
  Supabase call degrades gracefully instead of 504-ing.
- Account states an admin can set: approve, suspend (`/suspended`), timed block
  (`blocked_until`, shows a neutral 503 like maintenance), force logout (`force_logout_at`
  bounces sessions issued before the stamp), rename, role (`service` marks non-human accounts
  like Lisa's mirror reader so they stay out of active-user counts).

- **Exam** `/exam/[subject]` — scored exam, writes `exam_attempts`.

- **Notes** `/notes/[subject]` — study notes with note-quizzes.

### Top 2 static area (`public/top2/`, gated)
Per board subject A-H, each folder carries: Reviewer, Strategy, Subject Exam, Preboards
(2025 + Sets 2-5), and topic sub-folders with cards. Plus `00-Master-Index/`: the CBLE
Simulator, OLE Mock Board (Set 1 + Set 2), Mock Reviewer, Daily Queue, cheat sheets.

Board subjects and OLE weights (from `src/lib/subjects.ts`, `SUBJECT_GROUPS`):

| Code | Subject | Weight |
|---|---|---|
| A | Ocular and Visual Biology | 10% |
| B | Physiological Optics, Binocular Vision and Perception | 15% |
| C | Primary Care and Refraction | 15% |
| D | Theoretical, Practical Optics and Ophthalmic Dispensing | 15% |
| E | Ocular Diseases and Ocular Emergencies | 10% |
| F | Clinical Optometry and Sub-Specialties | 15% |
| G | Ocular Pharmacology | 10% |
| H | Ethics, Jurisprudence, Practice Management and Public Health | 10% |

Note: the main-app banks split these into 16 finer slugs (see `SUBJECTS` in `subjects.ts`),
grouped up into the 8 board subjects by `SUBJECT_GROUPS`.

### Exam behavior difference (support should know this)
- **Subject exams** lock each answer on click and only move forward (no going back, no
  changing an answer). This is by design (learn-pace with per-question rationale). Users have
  asked about it; it is not a bug.
- **CBLE Simulator** is the review-style CBT: Previous / Next / First / Last, bookmark, and a
  Submit at the end, with answers changeable until submit. Its "all" for a single subject is
  capped near weight x 10 items from its own bank, so it is not the same set as a full subject
  exam.

## 10. Spaced-repetition (SRS) review queue

Logic in `src/lib/srs.ts`; server writes in `src/app/api/srs/record` and `.../grade`.

- Interval ladder: **1, 2, 3, 7, 14 days**. A new card is due tomorrow; each correct answer
  promotes it up the ladder; clearing the top rung retires it to "solid". A miss at any rung
  resets it to the bottom, due tomorrow.
- Day boundary is **Manila time** (UTC+8, fixed offset), so a card missed at 9pm returns the
  next day, not 11 hours later.
- Question identity across stacks: `questionId` is FNV-1a over the normalized stem plus a
  length suffix. The same question missed in the app and in a Top 2 page lands on one row.
- Pre-exam sweep: between `SWEEP_START` and `SWEEP_END` (2026-09-01 to 2026-09-21), retired
  cards get one final pass, spread across the days left, capped at 15 per session.
- Repairing a card after a question fix: run `exam-build/backfill_srs_payload.mjs --apply`
  (needs the service-role key), or run the generated `backfill_srs_payload*.sql` in the SQL
  editor. Both rewrite `question_reviews.payload` to the corrected content. Cards also
  self-heal the next time the source exam is sat.

## 12. Content pipeline (exam-build)

`banks/<S>.json` is the source of truth for Top 2 subject-exam content. The subject-exam HTML
under `public/top2/*/[A-H]-Subject-Exam.html` is a build artifact and must not be hand-edited.

Workflow:
```
python3 lint_bank.py            # flag guessable questions
python3 build_exams.py --check  # lint, then rebuild all 8 subject exams
python3 build_exams.py A G      # rebuild named subjects only
```

Add questions: write to `additions/<S>.json` with the correct answer as **text** in `ans` and
only the wrong options in `o`, then `python3 add_questions.py <S>`. The merge assigns the
answer's position, so an author never picks the index (this is what stopped the bank drifting
to a guessable answer position). Duplicate stems are rejected.

Fix a flagged question: rewrite its options in `patches/<S>.json` and run
`python3 apply_patch.py <S>`. Patches touch options only, never the stem or explanation.

The linter blocks test-wise tells: a gloss only on the answer, the answer being the longest
option, hedging only in the answer, absolutes, "all of the above", duplicate options or stems,
a bad answer index, and bank-wide answer-position skew.

Runtime fairness (in `template.html`): options reshuffle on every attempt with the index
remapped, so the authored position never reaches the student. Bare-quantity questions (`n:1`)
sort ascending like a real board paper.

Important caveat: **preboards, mocks, and some cards are NOT rebuilt from `banks/`.** They are
their own HTML with embedded question JSON, so a fix there is a direct edit to the page (and,
if the card is already in someone's queue, an SRS backfill). This is the dual-source problem
in section 15.

## 13. Admin capabilities

Admin UI at `/admin`, backed by `src/app/api/admin/*` routes (service-role, server-side):

## 15. Known issues and tech debt

The consolidation analysis is in `docs/ARCHITECTURE-CONSOLIDATION-PLAN.md`. The headline:

- **One question, many homes.** The same item can exist in a bank, in `src/data/*`, and in one
  or more static preboard/mock pages, each with its own key. Fixes have to be applied to every
  copy or they drift. The elderly-bright-sun-glare item (fixed 2026-09-16) is a live example:
  the preboard page and the SRS snapshot disagreed with the subject-exam bank.
- **Behavior duplicated across 162 static files.** Tracking, access gating, and SRS reporting
  had to be hand-injected into each Top 2 page; every change is 162 chances to miss one.
- **Two quiz engines.** The React exam engine and each static page's embedded quiz JS behave
  differently (for example the subject-exam one-way lock vs the simulator's reviewable CBT).

Target after boards: one Next.js app, one question store, one quiz engine, one reviewer
renderer, Python reduced to data-prep only. Phased, redirect old URLs, no big-bang rewrite.

Interim rule to stop drift: one source of truth per question. If an item is in `src/data`, do
not also embed it in a static page, and vice versa. New Top 2 content is authored in the data
store, not as new HTML.

## 17. Common maintenance runbooks

**Fix a wrongly-keyed question**
1. Find every copy: search `src/data/*`, `exam-build/banks/*`, and `public/top2/*.html` for the
   stem. Remember preboards/mocks are their own embedded copies.
2. Correct the key and rationale in each copy. Rebuild subject exams from banks
   (`build_exams.py`); edit preboard/mock pages directly.
3. Commit and push to `main` (Vercel auto-deploys the static pages).
4. Repair existing review cards: run `backfill_srs_payload.mjs --apply` with the service-role
   key, or run the row's UPDATE in the Supabase SQL editor. Verify with a SELECT on the
   `question_id`.

**Deploy**
Push to `main`. Vercel builds and deploys. There is no separate release step. For risky
changes, push to a branch and use the Vercel preview URL first.

**Toggle maintenance mode**
`/admin` maintenance toggle, or set `app_settings.maintenance_mode = true`. Non-admins get a
503; admins and sign-in paths stay up.

**Approve / suspend a user**
`/admin` users tab (approve, suspend, block, force-logout, rename, role, grants). These call
the service-role admin API; do not try to do it with the anon key.

**Apply a schema change**
Write or update a file in `supabase/`, then run it by hand in the Supabase SQL editor. Files
are written to be idempotent and safe to re-run.

**Add Top 2 content**
Author into `banks/` (subject exams) and rebuild, or the data store for new content. Add a
`reviewer-manifest.ts` entry so it becomes grantable, then grant it per user in `/admin`.

## 19. Glossary

- **Top 2:** the premium/curated content area (named for the Top-2-finish goal). Today it is
  the static `public/top2/` pages; access is gated by tier + grants.
- **Cockpit / master index:** the map of all Top 2 content. Static index is admin-only; others
  get the dynamic `/reviewer`.
- **Floor:** the daily review-queue target (the SRS cards due that day).
- **Sweep:** the pre-exam final pass over retired SRS cards during the taper window.
- **CBLE:** the computer-based board exam format the simulator mimics.
- **Preboard:** a practice set modeled on a real preboard paper, one of several sets per
  subject, stored as its own static page.
